### 3.2 数据库内优先的提示词草案

**用户已确认的要求：在数据库内可以完成的计算和分析，优先在数据库内完成。** 该要求不是待选择项；以下提示词措辞和实现方式可以完善，但不能退回旧协议的“SQL/Python 自由分配”。

原始英文任务和 schema 原样保留，在独立的执行协议段添加以下内容；它是本地实验约束，不伪装为 benchmark 原题。

```text
Perform filtering, projection, joins, grouping, aggregation, ranking, window
calculations, and arithmetic or conditional scenario calculations inside the
supplied database whenever its SQL capabilities reasonably support them.

Use Python primarily for visualization and statistical procedures that are not
reasonably supported by the supplied SQL engine. Retrieve only the columns and
rows needed for those steps. Do not export the full table merely to reproduce
SQL-capable filtering, joins, or groupby operations in pandas.

Before a Python analysis call, briefly state its purpose and why that part is
being performed outside the database. This is an execution-location explanation,
not a prediction of future queries.

Choose queries based on the task and observed results. Do not target a query
count, split queries to increase trajectory length, or perform analyses solely
for this experiment. CTEs, subqueries, and window functions may be used naturally.

All database access, including access initiated from Python, must use the logged
database execution interface. Never bypass SQL recording. Do not access reference
answers, evaluation materials, other tasks, or previous trajectories.
```

“优先”不等于“只许 SQL”：SQL 缺少合适统计函数、绘图需要原始点、任务确实需要必要明细时可以用 Python。判断标准是功能和数据需要，而不是“Pandas 写起来短”。不要要求用户为每次 Python 使用单独批准。

Python 理由和实际源码都要保存；事后记录是否符合协议。理由只是模型自述，不能独自作为合规证据。不因一次不合规就自动重跑，应保留轨迹并明确标记。

执行位置按以下规则检查：

| 工作 | 默认执行位置 | 例外说明 |
|---|---|---|
| WHERE、Join、GROUP BY、排序、Top-K、窗口计算、分箱统计、常规条件/算术模拟 | 数据库 SQL | 不以“Python 更方便”作为迁出理由；必要例外记录具体功能限制 |
| 绘图所需的聚合、筛选、抽样 | 先 SQL 准备必要结果 | 不能因为最终要绘图，就默认导出全表做所有前处理 |
| 图形渲染 | Python | 使用 SQL 已准备的结果；确实需要明细点时只取必要数据 |
| SQLite 不便支持的统计检验或数值算法 | Python | 尽可能先在 SQL 中完成筛选、Join 和可合并统计，再传入必要输入 |

这是一项计算位置约束，不是查询长度约束。允许用一条 CTE/窗口 SQL 完成多步分析，不设置最低 SQL 数。最终报告独立列出 Python 的用途和协议例外，不能将违反数据库优先协议的轨迹混称为严格符合协议。

此协议可能改变轨迹长度，正式名称应为“数据库内优先协议下的 Agent 轨迹”，不声称代表所有默认 Data Agent。

## 4. 统一 SQL 记录：先解决“到底执行了什么”

### 4.1 一条语句一条事件

在数据库执行入口记录语句尝试，并配合 SQLite 执行追踪记录实际送入引擎的语句。trace callback 本身可能看不到准备阶段就失败的 SQL，因此不能只靠 callback；调用日志和引擎日志须按执行 ID 对齐。

覆盖：query-db、list-db、连接 PRAGMA/事务语句、Python 发起的数据库调用、批量调用和多语句脚本。参数化 SQL 同时保存模板和绑定参数；动态生成 SQL 保存运行时文本，不能只保存 Python 源码里的模板。executemany 保留每组参数和实际执行次数。

同一 SQL 被包装层与引擎层都记录时合成同一个执行事件，不算两次。工具调用可以包含多条 SQL，SQL 数按语句尝试数，不能按工具调用数。被调用上限拒绝而没有送入数据库的请求另列，不冒充引擎执行。

要求所有数据库访问走统一入口；Python 如需访问数据库也通过该入口。补充检查 Python/工具命令是否绕过日志。若当前实现不能保证某条路径被追踪，必须标记覆盖缺口，不能只凭正则搜索就宣布运行时完整。

### 4.2 记录字段与编号

| 字段组 | 内容 |
|---|---|
| 身份 | 批次、任务、attempt、工具调用 ID、SQL 执行 ID、父调用、连接 ID |
| 顺序 | 单轨迹稳定序号 S1、S2…；开始/结束时间；SQL 来自何处；与 Python 步骤的先后关系 |
| 内容 | 原 SQL、参数、引擎实际语句、数据库标识、方言 |
| 类别 | data / metadata / connection_setup / maintenance / unknown；有歧义不强行归类 |
| 状态 | 请求、已尝试、成功、失败、取消、超限；错误文本与执行覆盖状态 |
| 结果 | 列名/类型、完整行数、原始行数组、归档路径、哈希、是否完整；保留重复列名 |
| 成本 | 执行返回、执行并取回、编码落盘分别计时；勿相加重复计时；不把 EXPLAIN 估算当实测扫描行数 |

全部 SQL 用 S 编号；数据查询可另给 Q 编号，但必须有 S↔Q 映射。Python 步骤 P1…穿插在同一工具时间线上。数据准备、官方评分、离线候选验证的 SQL 单独标 phase，不能混入 Agent trajectory。

原始数据库保持只读；物化、索引等离线实验写入独立临时库或副本。完整结果采用流式归档与哈希；预览可以截断，归档完整性必须明确。停止任务时检查子进程和未完成 SQL。

## 5. 工作负载统计：先说明实际工作，再说明优化

执行 Agent 应先将下列方案整理成简洁的数据字典 `METRICS.md`，落实字段、口径和示例；实现时遇到引擎/语法差异可完善，但不能悄悄改变口径。最终汇总由结构化数据自动生成，避免手抄数字不一致。

### 5.1 第一张表：100 个任务的总览

建议每行一个任务，主表控制在以下列：

| 任务 | 一句话题意 | 数据库表数/大小 | 运行状态 | 全 SQL 尝试/成功 | 数据 SQL 尝试/成功 | Python 次数 | 时长 | 分析覆盖 |
|---|---|---|---|---|---|---|---|---|

“正常提交”“超时”“额度中断”等与“官方未评分”分开，提交报告不叫答案验证成功。顶部列计划 100、已开始、正常提交、各类中断和未开始的数量；数量必须闭合。

SQL 长度分布给均值、中位数、P25/P75/P90、范围，并同时说明样本量和分母。未截断轨迹与截断轨迹分开描述；保留失败/未提交轨迹，不能只对看起来好的任务统计。

### 5.2 第二张表：逐条 SQL 做了什么

每题一张主表；默认展示数据 SQL，元数据/设置另表，但所有 S 编号必须可查。

| SQL | 用途 | 状态 | 基础表 | Join 输入数/类型 | GROUP BY 维度 | 聚合操作与输入列 | 结果行数 | 数据库耗时 |
|---|---|---|---|---|---|---|---|---|

表内用具体内容，例如 `SUM(revenue), AVG(cost), COUNT(*)`；长表达式展开在该 SQL 的详情中。不要只写一个让读者无法解释的“聚合=7”。用途由原任务和 SQL 说明，推断意图要标明，不伪装成 Agent 自述。

### 5.3 表、Join、分组与聚合的统计口径

| 维度 | 必须保存的明细 | 轨迹内怎样汇总 |
|---|---|---|
| 基础表 | 解析到 database.schema.table；CTE/子查询不是新基础表；保留表引用次数 | 访问 0、1、2、3、≥4 张不同基础表的 SQL 各多少条；另列无法解析数 |
| Join | 每个查询块的 Join 类型、输入关系实例、条件、基础表血缘；自连接两个输入但可能只一张基础表 | 无 Join、最大 Join 组件为 2、3、≥4 个输入的 SQL 数；另列 INNER/LEFT/CROSS 等出现数 |
| 多层查询 | CTE、子查询、集合运算的作用域图；不要把不同子查询访问的表都算作一个 Join | SQL 主表显示最复杂 Join 组件；详情列出各组件及其输入。多表访问不等于做了多表 Join |
| GROUP BY | 每个查询块的规范化分组表达式，解析别名和位置引用；维度数量按分组键表达式计 | 无显式分组、最大 1、2、3、≥4 维分组的 SQL 数；完整保存维度向量，避免只给最大值丢掉内外层差异 |
| 聚合函数 | 每处 COUNT/SUM/AVG/MIN/MAX 等、DISTINCT/FILTER/CASE、所属查询块、聚合输入列血缘 | 每种函数出现在多少条 SQL 中，另列表达式总数、不同输入列数；一条 SQL 可包含多个函数，列间不应强求互斥 |
| 聚合输入列 | 指标计算依赖列与条件控制列分别保存；如 SUM(CASE WHEN region=… THEN revenue END)，保留 revenue 指标及 region 条件 | 回答“对哪些列做什么聚合”；COUNT(*) 单列为行计数，不虚构一个输入列；AVG(a/b) 保留 a、b 及完整表达式 |
| 窗口计算 | OVER 的函数、PARTITION BY、ORDER BY、窗口范围 | 单独统计；PARTITION BY 不计为 GROUP BY；窗口 SUM 不混入普通分组 SUM |
| 筛选 | WHERE/HAVING/CASE 中条件分开，记录字段、值和范围 | 描述访问范围；只有后续兼容性验证才把共享筛选变成优化候选 |

一般分布以成功数据 SQL 为分母，失败 SQL 单列。SQL 解析、表血缘、列血缘覆盖分别报告；无法识别的 JOIN/GROUP BY/聚合标 unknown，不填 0。遇到 GROUPING SETS 等复杂语法保留实际分组集，不用简单表达式数误报维度。

“几表 Join”的主口径是同一 Join 组件的关系输入实例数；必须同时保留不同基础表数，解释自连接和 CTE Join，避免把两者混为一谈。

### 5.4 第三张表：每条轨迹的结构分布

为可读性拆成两张平行表，不造一张二十多列的宽表：

- 表 A：任务、成功数据 SQL、单表/多表 SQL、含 Join SQL、2/3/≥4 输入 Join 分布。
- 表 B：任务、含 GROUP BY SQL、1/2/3/≥4 维分组分布、含聚合 SQL、各聚合函数 SQL 数、含窗口 SQL。

100 题逐任务 CSV 完整提供；正文各给一张紧凑表或分段表，点击任务 ID 进入详情。JSON 保存所有深层结构，不要求读者先看 JSON。

## 6. 每条轨迹内的优化机会分析

### 6.1 分析什么

逐任务独立分析，既看相邻 SQL，也看较早查询与多个后续查询的关系；不只看相邻对，更不跨任务拼接。

按以下层次区分，不能合并成一个模糊的 overlap 数：

1. **已有结果直接复用**：真实前序结果已经足够回答后续查询，检查它是否在 Python 中已被复用。
2. **额外构建共享中间结果**：需要新增过滤表、Join 结果、聚合 MV 或具体公共子表达式，才能服务多条 SQL。
3. **仅结构相似**：同表、同列、相同 COUNT 等只是筛选候选的信号，不计入已验证机会。

候选类型包括 exact-result reuse、common filtered view、shared join、aggregate MV、common subexpression。不要机械要求每题每类都有候选；没有合适候选时说明原因。

### 6.2 必须检查的兼容性

- 来源表、Join 条件/类型、重复行语义、过滤范围、NULL 语义是否兼容。
- 候选是否保留后续需要的分组键和列；粗粒度结果不能恢复已经丢失的细维度。
- AVG 使用 SUM 与对应非空 COUNT；DISTINCT 不能直接相加；比值、CASE 条件和四舍五入位置须保持语义。
- 处理 ORDER BY/LIMIT、并列值、集合重复语义；有顺序要求时比较顺序，无顺序要求时比较多重集。
- 浮点误差、完整结果限制、非确定函数或数据变化导致的比较限制要明示。
- 共享 Join 的成本和输出膨胀、候选的行数/列宽同样重要；不要默认中间结果必然更小。

### 6.3 每个候选一行，给出可查证据

| 候选 | 类型 | 原有结果还是新增物化 | 最早构建点 | 受益 SQL | 覆盖率/后续次数 | 中间规模 | 验证状态 | 成本结论 |
|---|---|---|---|---|---|---|---|---|

候选详情保存 build SQL、每条 rewritten SQL、原查询 ID、结果比较方法与记录。后续复用次数不含触发查询；覆盖率明确分母是该轨迹成功数据 SQL，是否包含触发查询。多个候选覆盖同一查询时做并集去重，不能相加成超过 100% 的“覆盖率”。

每题都要有分析状态：`已验证候选`、`有候选待验证`、`分析覆盖内未发现候选`、`轨迹/解析不足无法判断`。其中“未发现”是本轮方法的结果，不是不存在优化机会的证明。

### 6.4 分层验证，控制离线成本

第一层，对全部轨迹做结构解析和候选筛选；完整保留未覆盖语法。

第二层，对筛选出的候选逐题排序，**每题默认最多验证 3 个代表性候选**；其余仍列入候选清单但标未验证。优先多次受益、昂贵原查询、共享 Join、显著聚合压缩的候选。不要为凑候选数量构建整表副本。

第三层，实际创建临时中间结果并重放改写，比较归档原结果；原库保持只读。正确性不通过的候选不得进入已验证覆盖率。验证本身超时/结果过大时标受限，不算失败即不可能复用。

第四层，对少量最有希望的已验证候选测 build-vs-reuse。建议最多选 10 个、每题至多一个，选择规则和未测范围公开。先一次正确性重放，再固定 5 次串行计时、报告中位数与范围；基线和物化路径使用同一快照、同等连接/结果消费方式，交替执行、说明缓存状态。没有控制冷缓存就标暖缓存实验。每次物化路径都包含重新构建成本，不把构建只做一次再反复读的结果伪装成完整策略收益。

总成本比较：`T_baseline = 受覆盖原查询总成本`；`T_candidate = 构建并写入 + 受覆盖改写查询总成本`。索引、维护或额外状态构建如果使用了也计入；若分别报告纯引擎时间和端到端时间，边界须一致。不要把行数压缩比称为加速比。

本轮先做候选存在性及代表性性能验证，不以实现最优 MV 搜索算法为交付要求。离线分析的时间和资源上限也应配置并记录；触及上限时保留“未验证”，不静默减少分析分母。

### 6.5 与 Agent/FAD 研究的关系

附带保留结果依赖边：生产 SQL、消费 SQL/Python、使用的结果值或范围、间隔、题目指定还是 Agent 自选。不要仅凭字面值碰巧相同认定因果，也不要只记录紧邻 WHERE 而漏掉 CASE/Python 中介。

新增 MV 候选是事后利用完整轨迹选择的，必须标为 offline。记录假设构建点，但不要据此声称该时刻 Agent 已暴露必要信息。此次不增加 FAD 提示，不测 frontier 预测精度；它不是本轮四项交付的前提。

## 7. 文档怎么组织才容易读

### 7.1 总报告固定顺序

`REPORT.md` 按以下顺序组织，每部分以一句明确结论开头，然后给表和证据链接：

1. **这次跑了什么，跑完多少**：协议、数据范围、状态闭合表、官方未评分。
2. **轨迹有多长**：逐任务长度表和分布，Python 比例、预算截断、覆盖缺口。
3. **SQL 具体在做什么**：表访问、Join、GROUP BY、聚合分布，选少量真实 SQL 解释指标。
4. **哪些工作能共享**：逐任务候选状态总表、已验证覆盖及代表性成本，分开现有结果与新增物化。
5. **现在能得出什么、还不能得出什么**：只回顾有证据的观察，不把预设研究价值写成结论。

正文不堆所有 SQL、原始 JSON 或长统计定义。列名保持一致；“查询数”“查询对数”“候选数”“表数”写清单位，百分比旁给分子/分母，未知值用“未解析/未验证”，不用 0 替代。

### 7.2 每题详情统一模板

`tasks/dacomp-XXX.md`：

1. 一句话题意、数据表/行数/大小、运行与评分状态。
2. 一句话概括实际分析路线；若只是题目指定步骤，明确说明。
3. 逐 SQL 主表，并给全部 SQL/参数/结果链接；元数据/连接设置有单独入口。
4. Python 做了什么、为什么转出数据库、是否符合协议。
5. 优化候选表；最有代表性的 1–3 个候选给“原查询→共享状态→受益查询”的具体说明。
6. 一段本题结论：存在性、已验证收益、局限，不给空泛评分。

单条轨迹没有 Join、没有 GROUP BY 或没有候选，也使用同一模板，简洁说明，避免省略后无法判断是否分析过。

| 阶段 | 要做的事 | 通过条件 |
