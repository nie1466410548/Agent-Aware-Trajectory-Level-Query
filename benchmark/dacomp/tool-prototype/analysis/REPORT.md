# FAD 与实际后续 SQL 的匹配分析

分析日期：2026-09-09。结论：**在目前唯一的真实 Agent 提示轨迹中，FAD 对粗粒度访问方向有一定前瞻性，但结构化信息稀疏，且出现当前/未来访问混淆。不能据此认定已经获得高质量的任务级访问预测。**

## 1. 样本范围

| 任务/运行 | 是否可以评价真实 Agent 的 FAD |
|---|---|
| DAComp-006，hints-006-02 | 可以：30 次 SQL 尝试、26 次成功；29 份非空 FAD，最后一份 no_further_access |
| DAComp-006，hints-006-01 | 不可以：模型连接失败，0 次 SQL |
| 003、004、005 与 006 的 smoke/local-01 | 不可以：人工构造的联调提示，不是 Agent 预测 |
| 旧四题 natural 与后续百题数据库优先运行 | 没有本协议的 FAD，不能直接作为同次运行的预测真值 |

本次“实际轨迹”特指带 FAD 的同次 Agent 运行，未进行同配置 SQL-only 对照。模型、工具约束、Python 可用性不同的历史运行不能直接逐轮对齐。不能声称生成提示没有影响分析轨迹。

## 2. 评估方法

只匹配 **Q_t 的提示与 Q_{t+1} 及之后的 SQL**，绝不以当前 Q_t 作为预测命中。

结构化列匹配采用下一条成功 SQL 作为近期目标，另看剩余任务内是否存在匹配 SQL。Q7、Q8、Q14、Q18 失败，不作为成功访问目标；在这些轮次生成的提示仍保留，因为提示的范围是剩余任务。错误修复会推迟目标，故同时提供源查询成功子集的敏感性结果。

用 SQLite `EXPLAIN` 编译成功查询，通过 authorizer 的 SQLITE_READ 收集底层表列，无需执行数据查询。能覆盖 SQL 中的输入列、子查询、别名及过滤列；这是逻辑引用列，不是物理页面读取量或实际 I/O。初始 SELECT * 展开成真实列集合。

两个带 SQL 引号的提示列名，在分析时仅通过真实 catalog 的确定性拼写变体映射为规范名。例如 `sheet1."Consigned Product"` 映射到 `sheet1.Consigned Product`。原始日志和运行时的 unverified 标记不修改；同时报告严格原文匹配结果。

一个列在一份提示/一条目标 SQL 中只计一次；跨轮重复计数，因而这是逐提示观测统计，不是独立样本或统计显著性检验。多份提示可能对应同一个后续成功查询。

自然语言 `condition` 另行逐轮人工审阅，区分方向支持、部分支持、延迟支持、仅当前 SQL 支持和不可具体检验。不使用粗略表列命中替代语义判断，不将访问方向支持等同于计算正确或因果解释成立。

## 3. 结构化匹配结果

| 指标 | 结果 | 解读 |
|---|---:|---|
| 下一条成功 SQL 的表名匹配 | 29/29，100% | 本任务只有 sheet1，始终预测该表也会取得相同结果，区分力很低 |
| 提供列名的提示 | 16/29，55.2% | 前16轮提供列名，后13轮全部省略 |
| 所列列名全部出现在下一条成功 SQL | 14/16，87.5% | 采用确定性引号规范化；原文严格匹配为13/16 |
| 列级 micro precision | 35/38，92.1% | 38次“提示列”出现中，35次出现在相应下一条成功SQL |
| 有列名提示的 micro recall | 35/57，61.4% | 这16个预测目标实际需要的57次列引用，只明确预测了35次 |
| 全部29份提示的显式列覆盖率 | 35/123，28.5% | 无列名表示未提供信息，不表示预测“不会访问”；该指标衡量信息交付覆盖，不是惩罚错误预测 |
| 剩余任务中存在包含全部提示列的成功 SQL | 16/16，100% | 范围放宽且反复访问相同基础列，不能解释为完整意图准确率 |

源查询也成功的13份有列名提示：precision 27/30 = 90.0%，recall 27/47 = 57.4%，全部列近期匹配11/13。去除源查询失败轮次后，“较高精度但覆盖不完整”的结论不变。

所有29份非空提示只含一个候选；字段出现次数：tables 29、priority 29、condition 29、columns 16。filters、joins、group_by、aggregations、likelihood 均为0。

因此不能评估数值/等级概率校准、多候选资源分配所需的信息质量，或结构化谓词和聚合模式的准确率。priority 表示任务重要性，不是概率。

## 4. 一个简单对照揭示的信息增量问题

对25个“源SQL成功且仍有后续成功SQL”的前缀，比较两种信息：

| 描述下一条成功SQL所需列的方法 | 列precision | 显式列recall |
|---|---:|---:|
| 直接把当前SQL使用的列作为预测 | 76/119 = 63.9% | 76/102 = 74.5% |
| 当前FAD明确列出的列 | 27/30 = 90.0% | 27/102 = 26.5% |

这是离线、零模型成本的“重复当前列”参考，不是训练过的预测基线，也不是 SQL-only Agent 对照。它说明当前FAD更保守、列列表更短，但尚未证明相对SQL历史的综合优势。不能只看precision宣称更好。

在这些源查询成功的前缀中，FAD新增于当前SQL的列只在Q10和Q11出现：Q10提前指出产品列，Q11提前指出Date和Profit；其他有列提示大多重复当前已有列。自然语言仍可能包含额外的维度/方向信息，但尚未被完整结构化。

## 5. 实际例子与失败模式

### 有效的方向提示

- Q2 的提示说列出华南目的地，Q3实际执行 `SELECT DISTINCT Destination ... WHERE Destination LIKE 'South China%'`。
- Q5 的提示说按月、按省份分析利润，Q6按月和省份分组。
- Q6已经预告按产品分析月度利润，但随后继续省份分析、修复错误、列出产品，直到Q12才做相应聚合。这是符合任务剩余期间语义的延迟命中，不应因Q7不匹配就判错。
- Q18/Q19预告单位折扣和成本趋势，实际到Q28才出现。

### 说出了意图，却缺少关键结构字段

Q4在文字中说按月汇总利润，但columns只有Destination，漏掉Date和Profit。Q12/Q13提到性别/年龄，Q15提到年龄组，columns仍只有Date和Profit，未列出Customer Gender或Age Range。数据库仅消费结构化字段时就看不到这些分析维度。

### 列命中掩盖语义不匹配

Q16提示仍说按年龄组分析月度利润，但这正是当前Q16在做的事；后续没有相应年龄查询。下一条Q17进行收入成本月度分解，仍使用Date和Profit，所以列指标显示该提示100%命中，但“年龄分析”的未来意图没有发生。

Q20的省份×产品分析提示也只对应当前Q20；Q26的湖南月度利润提示只对应当前Q26。这三个案例均不能用当前SQL计入未来命中。

### 多个访问方向藏在一个自然语言字段里

Q22的condition列出广西、海南、河南、湖北、湖南五个省份。广西已经在当前Q22查询，后四省在Q23–Q26依次查询。后续提示依次缩短列表，却始终保留当前正在查询的省份。

这说明“每轮只有一个candidate”不等于只存在一个后续方向：Agent把多省份访问打包进了自然语言，同时混入当前访问。单纯统计candidate数量无法反映实际规划内容。

### 过于模糊或状态冲突

Q27的 `Additional analysis if needed` 没有足够具体的方向，不能因为之后发生任何查询就算命中。

Q29的condition写 `No further queries expected after this`，但结构status仍是provided，而且确实随后执行了Q30。最后Q30使用结构化no_further_access，后面没有SQL；这是单个终止判断正确的观测，不能推广成终止预测准确率。

## 6. 对设计的启示

1. **优先改善信息完整性。** Agent已在文字中提到的表列、维度和已知谓词，应尽量进入结构化字段；保留未知状态，不强迫编造细节。
2. **明确区分计划说明和触发条件。** 当前condition主要被当成“下一步要做什么”的描述，几乎没有表达条件依赖；可考虑独立的访问描述字段。
3. **收紧未来时间边界。** 强调排除当前SQL已经覆盖的访问，只有预计再次访问时才保留，并用额外标记区分重复访问预期。不能通过要求Agent执行提示来制造命中。
4. **让Schema覆盖真实访问形式。** 该任务频繁用Destination LIKE和strftime月份表达式；v0.1过滤算子没有LIKE，group_by只能列原始列。结构化缺失不能全部归因于Agent，需要同时检查接口表达能力。
5. **补充多题同配置对照。** 003/004/005需要真实生成FAD的运行，再考察多表、候选集合和不同阶段。当前单表单题不能验证完整研究主张。
