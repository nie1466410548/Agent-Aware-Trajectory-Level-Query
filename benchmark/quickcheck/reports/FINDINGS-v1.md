> 历史结论：结构重叠不代表多查询优化机会，当前结论请看 [FINDINGS.md](FINDINGS.md)。

# 九题快速验证：结论与可核查案例

已完成 Kimi 的 9 个任务 × 自然/FAD 两组，共 18 次运行，保存 146 条 SQL（108 条数据 SQL、38 条元数据 SQL）、45 份 FAD、完整工具结果和可见 Agent 消息。两组均有 7/9 题通过原始验证器，失败运行保留，未为提高通过率重跑。

**这批数据支持“真实执行轨迹中存在结构重叠，协作式 Agent 可以在下一条 SQL 可见输出前暴露访问意图”；尚不支持“已存在足够的有收益计算复用，且远期 rolling frontier 稳定可靠”。** 这是自定义 Kimi 适配器在真实 benchmark 数据上的运行；不是生产轨迹，也不是原作者 Agent 的复现。

## 1. overlap 是否存在

自然组发出 66 条数据 SQL，65 条成功。其中 44 条成功 SQL 与本轨迹前序成功 SQL 共享表，即 44/65 = **67.7%**；9 个任务都出现了这种重访。只看最终通过验证的 7 个任务，比例仍为 30/46 = **65.2%**。分母包含每个任务首次访问，因此这里是全部成功数据查询中的比例。分析仅比较同一任务轨迹内部的跨 query overlap，不将不同任务运行合并计算。

自然组有 37 条后续查询共享表和列；7 条包含与前序相同的 Join 片段，11 条包含相同聚合表达式。这些指标可以重叠，不能相加。相同表达式还可能在不同输入行上计算，不能直接当成可共享的聚合结果。

完全重复的规范化 SQL 为 0。当前保守规则识别出的直接结果复用候选也为 0：规则只覆盖完全重复、完整单表结果对后续简单查询的覆盖，排除了 LIMIT 抽样，未覆盖一般 Join 中间结果和聚合 rollup。**0 是检测范围内的结果，不是所有计算复用机会为 0。** 本次未采集物理扫描行集合、执行计划成本或实际复用后的时间，不能把同表比例解释为重复读取字节比例、可节省计算比例。

### 案例 A：同表重访不等于可复用完整结果

bookreview/query1 先 [抽样 SQL](../runs/natural/bookreview/query1/quick-01/sql/003-54f68a8495374a28bdff37a4b39e2755.sql)（LIMIT 5），随后统计、检查日期格式，最后 [完整读取 SQL](../runs/natural/bookreview/query1/quick-01/sql/007-c59919c876aa4580b6ad31fafb1e3310.sql)，再用 Python 计算。前面的样本不能替代最后的完整读取；这种轨迹会提高同表 overlap，却未必提供足够的物化收益。此任务自然组通过验证。

### 案例 B：同一 Join 上反复尝试不同业务口径

crmarenapro/query12 的 [按创建日期过滤](../runs/natural/crmarenapro/query12/quick-01/sql/003-36973557214b43df99082a9acece1394.sql)、[按签署日期过滤](../runs/natural/crmarenapro/query12/quick-01/sql/004-90615943ec654c9394fcdb8f7e8041fc.sql)、[按关闭日期过滤](../runs/natural/crmarenapro/query12/quick-01/sql/005-56d875618d494449b8ede6da9d81e7a2.sql) 使用相同 Opportunity–Contract Join 和平均周期表达式，但分别以不同日期字段限制 2023 年 4 月。它提供了值得检查的共同 Join/表达式候选。不过谓词下推会改变实际处理的数据，提前物化整个 Join 是否划算仍未知；该任务两组均未通过验证，不能只展示它的重复计算而忽略解题失败。

## 2. FAD 能否在未来 SQL 前暴露

FAD 在本实验中是 Future Access Descriptor：显式记录预计访问的数据库、表、列、过滤、操作和 1–3 条 SQL 的 horizon。协议要求先提交 FAD，收到工具回执后，在新的 assistant turn 中生成并提交 SQL；每次查询使用一次新回执。

45/45 次时序检查通过，其中 42 次针对数据 SQL、3 次针对元数据。检查未标记出在对应回执前的工具参数中提前出现完全相同 SQL。这个证据证明的是**可见消息/工具协议边界**，不证明模型在内部思考时尚未构思 SQL，也不等于无提示自然轨迹中被动预测未来。

数据目标的主要指标（按前瞻点宏平均）：

| 指标 | 结果 | 有定义的前瞻点数 |
|---|---:|---:|
| horizon=1 的下一条表精度 / 覆盖率 | 98.4% / 100.0% | 42 / 42 |
| 下一条列精度 / 覆盖率 | 85.0% / 90.9% | 42 / 39 |
| 下一条操作精度 / 覆盖率 | 93.7% / 89.3% | 42 / 42 |
| 过滤合取项精确匹配精度 / 覆盖率 | 28.6% / 29.0% | 21 / 20 |
| horizon 2/3 对第 2/3 条 SQL 表集合的精度 / 覆盖率 | 82.4% / 76.5% | 17 / 17 |

过滤指标采用严格结构文本匹配，语义等价表达式可能未匹配，因此不能解释为语义正确率。远期指标只在显式提供 horizon 2/3 的 17 个数据 frontier 上计算，不能推广到全部 42 个前瞻点；它匹配第 2/3 条 SQL 的表集合，不要求预测精确落在指定某一条。

FAD 到下一条 SQL 提交的间隔中位数为 **8.27 秒**（5.22–17.26 秒）。它包含额外模型生成与工具开销，不是免费的提前量，未测其中可并行准备多少工作。

### 案例 C：下一步准确，远期仍会落空

[FAD 组 crmarenapro/query8 的逐点记录](../runs/fad/crmarenapro/query8/quick-01/analysis.json) 中，FAD `185d3f2e1c0c4dacad4ba025923d9d3b` 正确预告下一步访问 support.casehistory__c，同时预告 horizon=2 访问 support.Case。但随后三条数据 SQL 仍访问 casehistory__c，Case 未在该窗口出现。该任务远期表精度仅 33.3%；crmarenapro/query12 只有一个远期前瞻点，精度为 0%。其余任务的小样本远期精度为 100%，显示明显任务差异。

因此，用“整个 frontier 对未来三条 SQL 的表精度 95.2%”单独论证稳定性会过于乐观：其中含非常准确的立即下一步。独立看第 2/3 条预测更接近我们关心的 rolling 能力。

### 案例 D：不少后续计算发生在 Python

[stockindex/query3 的 FAD 轨迹](../runs/fad/stockindex/query3/quick-01/analysis.json) 最终读取 index_trade 的 104,224 行，再通过 Python 分析投资回报。自然组也进行了完整读取与 Python 分析。两组共记录 12 次适配器 Python 调用；较长的 Agent 推理过程不必然产生较长的 SQL 链。本报告未将 Python 中间计算纳入 SQL 复用统计，原始 Python 源码和结果已保存以便后续检查。

## 3. 对研究方向的判断

- **已经有依据：** 在这 9 个任务中，同表重访普遍存在，部分任务出现重复 Join/聚合结构；要求 Agent 协作提交 FAD 的接口能够跑通，下一条表/列访问描述具有信息量。
- **目前证据不足：** 对实际数据范围的 overlap、值得物化的计算量、扣除准备开销后的收益、更远 horizon 的稳定性。每题每组仅一次，不能估计多次运行的稳定性。
- **最有价值的小步后续：** 直接从已保存的 CRM Join 口径变化案例中选择候选，核对共同输入范围，重放比较原 SQL 与共享中间结果方案的总时间（包括构建和读取）。不必先把全部 54 题跑完；若这个局部验证也找不到净收益，应重新审视优化对象。此建议尚未作为本次实验执行。

FAD 组数据 SQL 数由自然组的 66 变为 42，但多了 45 次 FAD 提交，可见 assistant 消息从 103 增至 162。两组是不同随机轨迹，且共享资源并发运行；这些变化不能用来宣称 FAD 提升效率。自然组失败任务是 CRM 8、12，FAD 组失败任务是 CRM 12、stockindex 2。

## 4. 可复查性与限制

所有 18 次运行均已结束；220 个带摘要的工具结果文件 SHA-256 校验通过，146 条日志 SQL 与 146 个独立 SQL 文件对应；4 个分析回归测试通过。可见轨迹审计的唯一非适配器 Bash 标记是读取本运行的 final.txt；Python 脚本读取已保存结果，未发现直接绕过适配器连接数据库的代码。访问限制依赖提示和只读数据库连接，非 OS 隔离保证。
